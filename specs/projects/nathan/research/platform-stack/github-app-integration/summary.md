# GitHub App Integration

## Bottom Line

Nathan needs **Metadata: read, Pull requests: read & write, Checks: read and Commit statuses: read**. It does not need Administration, Members or Contents, with one unresolved exception. Required checks can be found without Administration by using GraphQL **`isRequired(pullRequestNumber:)`** on `CheckRun`/`StatusContext`. This is the same mechanism `gh pr checks --required` uses, and it covers both classic protection and rulesets. A rulesets REST fallback needs only Metadata: read. The exception is **`markPullRequestReadyForReview`** (the only way to un-draft; REST has no `draft` field). Unofficial reports say an App may also need **Contents: write** for it, so verify before finalizing the permission set. The hourly sweep should be **one aliased GraphQL query** for all repos, costing about 18 points against a 5,000/hour budget. Fall back to a small second query only for PRs with failing checks, to resolve `isRequired`. On Workers, use **`@octokit/core` + `@octokit/auth-app` + `@octokit/webhooks-methods`**. This stack was verified to bundle and run in local workerd, with one hard rule: **convert the App private key to PKCS#8**, because Wrangler picks the Web Crypto build, which rejects GitHub's PKCS#1 PEM.

## Key Findings

- **Permission matrix from the docs' own data.** List/get PR, reviews and requested reviewers need Pull requests read. Check runs need Checks read. Combined status needs Commit statuses read. `POST`/`DELETE .../requested_reviewers` need Pull requests write. Classic branch-protection reads need **Administration read**. `GET /repos/{o}/{r}/rules/branches/{branch}` (rulesets) needs only **Metadata read**. Source: [permissions.md](./permissions.md), from `github/docs` `server-to-server-permissions.json`.
- **Ready-for-review is GraphQL-only, and its permission is undocumented.** REST `PATCH /pulls` accepts only `title, body, state, base, maintainer_can_modify`. A GitHub CLI maintainer suggested Apps also need `contents: write` for `markPullRequestReadyForReview`, and a 2024 follow-up said "This appears to be the case" ([cli/cli#6924](https://github.com/cli/cli/discussions/6924)). Test it. If it's true, either accept a down-scoped write token for that one path or drop the auto-ready feature.
- **Request reviewers via REST, not GraphQL.** REST POST is additive. GraphQL `requestReviews` has `union: Boolean = false` ("Add users to the set rather than replace"), so by default it *replaces*, which would violate spec §4.3. REST returns 422 "if user is not a collaborator", which is useful for modal validation.
- **`mergeStateStatus` can't isolate "required CI failing".** `BLOCKED` = "The merge is blocked" (reviews or checks or rules). `UNSTABLE` = "Mergeable with non-passing commit status". It works as a shortcut (CLEAN/UNSTABLE ⇒ no required check failing), not as rule 5. Use `mergeable == CONFLICTING` for rule 4. It is computed lazily: always *select* `mergeable` and treat `UNKNOWN` as "keep previous" ([community report](https://github.com/rjmurillo/ai-agents/pull/5463)).
- **Don't trust `statusCheckRollup.state`.** A 2026 report shows it changes depending on whether `contexts` is selected ([pvcnt/mergeable#189](https://github.com/pvcnt/mergeable/issues/189)). Compute failing/pending from `contexts`, deduping re-runs by name.
- **Org-membership classification isn't needed.** Spec §4.1 uses the user directory. `author_association` reports private org members as `CONTRIBUTOR` unless the caller has members:read ([HarperFast/harper#2773](https://github.com/HarperFast/harper/pull/2773)), so don't build on it.
- **Webhooks:** subscribe to `pull_request`, `pull_request_review`, `check_run` and `status`; `check_suite` is optional. `installation*` events are automatic. Skip `branch_protection_rule` and `repository_ruleset` (they need Administration read). **Fork PRs (OSS) get check events with an empty `pull_requests` array**, so keep a `head_sha → PR` index. GitHub expects a 2xx within 10s and "does not automatically redeliver failed deliveries", so the hourly sweep is the real backstop ([webhooks.md](./webhooks.md)).
- **Signature verification** is HMAC-SHA256 hex over the raw body in `X-Hub-Signature-256` (`sha256=` prefix), compared in constant time. Web Crypto `subtle.verify` does this. `@octokit/webhooks-methods` `verify()` reproduced GitHub's test vector in workerd.
- **Rate limits are a non-issue at this scale.** An installation gets 5,000 REST req/h and 5,000 GraphQL points/h (more above 20 repos/users, max 12,500; GHEC 15,000 REST / 10,000 GraphQL). Secondary limits: 100 concurrent, 2,000 GraphQL points/min, 80 content-creating requests/min ([state-model-data.md §4](./state-model-data.md)).
- **Workers specifics.** Wrangler resolves with `workerd, worker, browser` conditions, with no `node` condition ([wrangler source](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/deployment-bundle/bundle.ts)). That makes `universal-github-app-jwt` throw on PKCS#1, while its Node build silently converts, so Node unit tests won't catch it. Installation tokens last 1 hour, and auth-app caches them in memory per isolate; optionally back that with KV. Don't rely on `@octokit/webhooks`' `createWebMiddleware`: it awaits handlers for up to 9s and doesn't use `ctx.waitUntil`. Verify, then `waitUntil`/Queue, then return 202.
- **Trend metrics** come from `createdAt`, `mergedAt`, `reviews.submittedAt` and `ReadyForReviewEvent.createdAt`, all with Pull requests read. No MERGED_AT ordering exists, so page merged PRs by `UPDATED_AT DESC` ([metrics.md](./metrics.md)).

## Open Questions / Gaps

- **`markPullRequestReadyForReview` permission for an App:** is Pull requests: write enough, or is Contents: write also needed? Only unofficial 2022–2024 reports exist; docs.github.com has no per-mutation permissions. Needs a 5-minute test on a scratch repo.
- **`isRequired` with an installation token:** confirmed by third parties with user/CLI tokens only, and not tested with an App token here. No GitHub credentials were available in the sandbox. It also needs a per-PR argument, hence the two-phase query design. Needs a test.
- **Does `Ref.refUpdateRule.requiredStatusCheckContexts` include rulesets?** The schema says it covers "Branch protection rules that are viewable by non-admins", and is silent on rulesets. Only matters for fallback Option B.
- **No live GitHub API calls were made.** Sweep cost (~18 points) is computed from the published formula, not measured. Use `rateLimit { cost }` in development.
- **docs.github.com was blocked** by the sandbox proxy. All GitHub doc citations come from the `github/docs` repository source (same content, rendered from these files) and are linked by their public docs URLs.
- Whether merge-queue repos need `merge_group` handling was not verified; that depends on whether the team uses merge queues.
